# One protected position in a live-room footprint

The hosted server check runs on pushes to `experiment/live-room-position-privacy`. Each run records its source commit. The preceding chest check used `7c4e6492e1221573c098748a250ae57a6c81e377`. That passing test covered chest activity. The position policy withholds raw destination columns from every remote viewer. The current protection hook answers for one player at one position and supplies no authoritative region grant or invalidation revision. At the shipped height of 256, the 5×5 footprint spans 1,638,400 positions. The heights, palettes, biome and light data in an initial column can also describe positions outside the visible patch. Checking eight pads, a column center or a previous tick cannot certify those bytes. [Previous chest-privacy result](https://github.com/WeepingAngeIs/zSortange/actions/runs/44402820529)

The position policy gates raw View admission and retained loading before a remote portal is published. The final send check independently requires an actual Visit in the corresponding pocket for protected world data. An independently authorized diagram and a physical visit are the positive controls that exist today. The remote admission check gives even a fully trusted home viewer the fallback. Selective live terrain for such a viewer remains open. Live admission, physical travel, saved items and the public artwork have separate responsibilities. No change to the production JAR is part of this draft.

## What the hosted job exercises

The first boot starts a fresh Java 21 dedicated server with the reviewed art.2 Storage Plus JAR. It creates two rooms, grants ordinary home View permission, and sends a registered test player through the normal physical Visit and return paths. A test listener denies a second player access to one decoration position. The fixture decodes a prepared column to confirm it contains the marker and evaluates real Minecraft packet objects using the policy classes packaged in the experimental adapter. Connection cleanup uses simulated listener identities and delivery callbacks. The job compares a remote refusal during a real chunk save with a separate server process reading the saved marker and room ledger from disk.

The artifact contains `position-privacy.json` for the first boot, `position-save-oracle.json` for the save, `position-restart.json` for the second boot, the two logs, and source and binary checksums. The presence of all three records and a successful job are required for this server check. The broader acceptance cases below include observations that require a running CE client, a rendered diagram or a recovery fixture.

## Setup

Use a fresh disposable dedicated server with two distinct pockets. In room A choose an ordinary editable block away from all eight chest pads, in a column containing no block entities. Record its height, column and original state. Use a plain, visually distinguishable block as a marker. A chest would make the old chest-data filter an alternative reason for denial.

Use three non-operator identities. Give Guest and Owner permission to view A from home. Give Visitor a physical Visit to A. Install an owned fixture listener patterned after `PadPreviewProbe.exactEmptyPad`. It denies only Guest at the marker's exact coordinates in the pocket dimension. Before testing, call the ordinary permission hook at the marker and its neighbor. Record the real actor, dimension and results. Guest must receive exactly the intended denial. Owner and Visitor must pass the same marker check. The bulk remote restriction applies even to Owner. A missing listener, absent marker or inactive visitor invalidates the setup.

Exercise two cleanup transitions in the server-side fixture. Remove a CE watch before reconciliation and require one forget for its column only if that connection previously received it. The replacement must keep its own ledger and must never inherit the old socket's column or entity IDs. A forget or entity removal may reference previously delivered data for its own recipient. Previously received bytes cannot be recalled.

## Positive criterion for selective remote views

The containment checks above cannot prove that one remote player can see a block another player cannot. Before enabling actual room pixels, require that positive and negative result from the **same marker**. A bounded first design is one fixed decoration position, already loaded, with no entity or inventory payload. Queue only the intended recipient, connection, room identity, epoch and sample position. At delivery, recheck the live session, home permissions and claims, then ask the existing destination hook for that actor and exact position. Read a fresh allowlisted plain material only after permission succeeds. An unavailable or denied cell uses a fixed neutral value. An old sampled material must never be queued for later reuse.

Use two plain non-emitting materials, for example cyan and purple concrete, with identical geometry. Hold the camera, public geometry and capture timing fixed. With both players permitted, require both to observe the first material. Deny Guest only at that position, change the real marker, and require Owner's sample to change while Guest's output stays neutral. Changing the marker again or reverting it while Guest is denied must produce identical Guest output, including message presence and length. Reverse the players' permissions for a third observation. A neighbor, an unloaded cell, an unknown block and a revoked session are separate controls. The experiment must create zero remote loaders and keep the diagram available. If multiple cells are combined later, their decisions need a consistent publication boundary. A one-cell result cannot authorize a whole packet.

Only a representation constructed from those authorized samples and fixed public defaults can qualify for that test. Reusing the original section palette, heightmap, light arrays or block-entity records would reintroduce the larger disclosure. This is a design for follow-up verification. This draft adds no sample protocol, renderer or entrance activation.

## Evidence and execution decision

Record packet type, producing action, tick, actor, room, queued time, final disposition and applied state for each required case. Record the positive controls and ownership counts alongside denials. A direct call to the exact final filter can test a prepared packet that a refused preview could never enqueue. Label that case as a server-side check. Zero deliveries alone cannot prove packet handling when the packet was never produced. For a network claim, also observe the final server connection boundary and the actual client after packet application. Check the destination cache for the marker and entity. Keep simulated and observed results separately identifiable. This test cannot establish framebuffer, full-pack or physical-GPU acceptance.

The hosted job records the checked-out commit, loaded Storage Plus and policy hashes, and the safety, CE and fixture artifact hashes. The safety module and CE are build inputs for this job. The prior three-client CE runner requires beta.6 and enforces its own input hashes. An end-to-end test must retain its pinned CE 6.1.4 source `ad2e7ee5d73e4ff78bd0befade4f797265e65939`, exact renderer dependencies and software display. A combined art.2 and CE test needs a separately reviewed compatibility lane. Keep the beta.6 guards intact and report each result against the binary it actually exercised. The experiment's entrance remains disconnected from live terrain.
