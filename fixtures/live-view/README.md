# Experimental scoped live-view adapter, not installation approval

This separate module is default-off behind `anyastorage.liveViewPrototype`. It requires the already approved CE 6.1.4 source `ad2e7ee5d73e4ff78bd0befade4f797265e65939`, exact verified Sodium 0.8.13 / Iris 1.8.14-beta.1 (installed, shaders off), Minecraft 1.21.1 / NeoForge 21.1.249 and the unchanged safety/operator module. Production files, saved formats, artwork, current beta.6 and the non-live preview are not changed.

The initial subset streams terrain and the existing restricted StorageEntity update tags. Remote entity preview is denied; physical visitors retain scoped entity spawn/update handling. Unknown protected packet families or block entities are refused, not serialized wholesale. This is not arbitrary-mod compatibility. Public registered dimension IDs are not secret; recipient-specific portal coordinates and destination contents are gated.

A maximum of eight handles, two per player, cover at most two newly admitted pockets. Each has its own absolute 1200-tick deadline. Preview checks are loaded-home identity, existing spherical range/claims and View permission; no Visit/storage/Build right is created. Existing Visit/recovery records and tickets are not replaced. All CE protected-destination base loaders are filtered and replaced with a 25-column radius-plus-halo envelope per pocket; source-world loaders are unchanged. Nested protected-dimension queries and extra/global protected loaders are refused. The resource watchdog closes/refuses previews, never evicts required chunk saves or visitor/recovery tickets.

Pinned scoped mixins invalidate only unauthorized player/column watch records and pending sends. A final server-listener gate recursively validates redirected packets and bundles after CE wrapping, using fresh authorization. Previously authorized bytes already handed to TCP cannot be recalled from a malicious client; ordered forget packets clean the compliant client's cache. Portal invisibility is not used for revocation or unloading.

The acceptance module is separate from the adapter and uses three actual Minecraft clients over loopback TCP, two production pockets, explicit fixture permissions/items and an unauthorized observer. It exercises mixed visitation, stale queued packet refusal, independent handles, socket loss/reconnect, range and anchor loss, cleanup while clients remain connected, force-save and independent primary/item/identity restart checks. Any pass must identify the exact executable and packet/resource evidence; source design alone is not proof.

No user profile is read or launched. No new third-party runtime beyond the approved lane is permitted. Source builds and heavy tests belong on bounded GitHub runners. The renderer is software Mesa, not target-GPU/full-pack certification. Packet instrumentation and fixture orchestration are not an uninstrumented performance benchmark. Clean stop/restart does not solve arbitrary power loss or non-atomic player/chunk/ledger/POI transactions; no durable newest copy still means unrecoverable newest bytes.

## Connecting the current entrance to the live experiment

The beta.7-art.2 entrance draws an illustration on the horizontal face the player looks at. A viewer with permission at the home entrance can see an eight-position chest diagram when the room is already loaded. The earlier CE experiment instead opens a separate 3×3 plane above the entrance by pocket ID. Its three-client trial checked delivered room data, scoped unloading and persistence. The separate red-to-green renderer control used a diagnostic wall. Neither trial captured the actual pocket through the current illustrated face. [Illustrated entrance trial](https://github.com/WeepingAngeIs/zSortange/actions/runs/44394403209) · [Pinned live experiment](https://github.com/WeepingAngeIs/zSortange/actions/runs/44155633073) · [Renderer control](https://github.com/WeepingAngeIs/zSortange/actions/runs/44092751116)

The experimental `experiment/live-room-chest-privacy` branch addresses chest activity at the final outgoing packet check. The reviewed chest includes `LidOpen` in the initial chest data and later updates, even when it is closed. Its open and close transitions also generate block events. A remote observer's authorization to see the room does not grant visibility into that activity. The allowed block-entity data remains limited to the public symbol and label setting. Protected block events require a valid physical visit at the event's position. A visit to a different pocket does not satisfy that condition. Packets containing unsupported fields are withheld whole. The diagram and the ordinary storage UI keep their own behavior.

### Remaining privacy and rendering work

The existing destination permission hook accepts one actor, dimension and exact position. The current diagram checks all eight positions, including empty pads. The CE experiment can send full encoded columns in a 5×5 footprint, including neighboring terrain required to render the room. Permission at the home entrance, at the chest pads, or at one sample per column cannot establish permission for all that data. The branch leaves live activation at the illustrated entrance disabled. A later step needs a bounded way to authorize exactly the terrain sent, or to assemble a smaller terrain representation containing only authorized positions. It must account for light, block updates, unknown block entities, stale queued data and changes to permissions, and fall back when it cannot establish visibility.

Once that boundary is demonstrated, the entrance still needs to align the private portal with the selected face, show the public or authorized diagram again when the session ends, and avoid turning continuous gaze into successive lifetime extensions. A target test would change one permitted decoration in the real pocket, measure the change in that exact entrance's pixels, and show that an unauthorized observer keeps the fallback throughout. The archived beta.6 workflow keeps its original binary pins. This branch provides no installable live adapter or release approval.
